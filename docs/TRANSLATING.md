# Translating FM-1 Companion

FM-1 Companion is written with **English** as the source language. Every text the user sees is English in
the code and wrapped in a translation function. Translations are plain gettext `.po` text files – one
folder per language, several files per folder. German (`de`) is the first translation.

No build step is needed: the app reads the `.po` files directly (`fm1companion/i18n.py`). There are no
`.mo` files to compile and no extra packages to install.

## Choosing the language

* **Settings › General › Language**: *System language* (default), *Deutsch*, *English*, … – takes effect
  after restarting the app.
* *System language* uses the system locale (`LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`) if a
  translation exists for it, otherwise English. A German system gets German.
* For one start: `fm1-companion --lang en` (or `--lang de`).
* For tests and debugging: environment variable `FM1C_LANG=en|de|…` (overrides the setting).

Qt's own texts (file dialogs, standard buttons, context menus) follow the chosen language when Qt's
translations are installed (Debian: package `qt6-translations-l10n`).

## Layout

```
fm1companion/
  i18n.py                     # _(), ngettext(), pgettext(), N_(), set_language() … (no Qt)
  locale/
    messages.pot              # template, generated by tools/i18n_extract.py – do not edit
    de/
      frame.po                # window, menus, sidebar, status bar, settings, about …
      firmware.po             # one file per area of the app (added as pages are converted)
      …
    en/README.md              # English is the source – nothing to translate
  data/help/
    de/*.md                   # help pages in German (complete set)
    en/*.md                   # English help pages (missing pages fall back to German)
```

All `.po` files of a language are merged. Splitting by area lets several people work on one language at
the same time without editing the same file. The same msgid may appear in two files of one language only
with the same msgstr (the checker reports a conflict otherwise).

## Writing translatable code

```python
from ..i18n import _, N_, ngettext, pgettext

button.setText(_("Save"))
label.setText(_("Saved {n} files to {folder}").format(n=n, folder=path.name))
status = ngettext("{n} file", "{n} files", n).format(n=n)
menu.addAction(pgettext("menu", "Open"))         # context: same English word, different meaning
TITLES = {"ok": N_("Everything fine")}           # marked only; translate when used: _(TITLES[key])
```

Rules:

* **No f-strings inside `_()`.** The extractor needs a literal. Write `_("Hello {name}").format(name=x)`,
  not `_(f"Hello {x}")`. Use **named** placeholders so translators can reorder them.
* Keep placeholders exactly (`{name}`, `%s`): the checker fails if a translation drops or invents one.
  In plural forms a translation may leave out `{n}` (e.g. German "eine Warnung").
* **Plurals** always with `ngettext(singular, plural, n)` – never `"file" if n == 1 else "files"`.
  Languages with more plural forms set them in the `Plural-Forms` header of their `.po` file.
* Whole sentences, not fragments glued together: `_("Backup saved: {name}")` rather than
  `_("Backup saved") + ": " + name`.
* HTML / rich text is fine inside a msgid (`_("<b>{n}</b> found.")`); translators keep the tags.
* Keyboard accelerators (`&File`) and `&&` (a literal `&` in Qt labels) stay in the msgid; translators
  choose their own accelerator letter.
* **Never translate**: log messages (`log.info(...)` stays English or as is), protocol identifiers, SysEx,
  JSON keys, settings values, file and folder names on disk or on the device, command lines, URLs,
  page keys (`"overview"`), and texts written into files meant for developers (bug report contents).
* Don't use `_` as a throw-away variable (`path, _ = QFileDialog.getSaveFileName(...)`) in a module that
  imports `_` – Python then treats `_` as a local variable in the whole function and `_("…")` fails.
  Write `path, _filter = …`.
* Search keywords (`PageSpec(keywords=…)`) are **not** translated: list German *and* English words so the
  command search works in both languages.
* The language is fixed for the whole run of the app. Module-level constants may use `_()` (they are
  translated once at import); `N_()` + `_(value)` at the place of use works too.
* For German text that must stay as it is in the code (e.g. a German file name on the device), add the
  comment `# i18n: ignore` to the line so the "German left" scan skips it.
* A comment `# Translators: …` directly above the call is copied into the template as a hint.

## Adding or updating a translation

1. Regenerate the template after changing strings in the code:

   ```
   python3 tools/i18n_extract.py
   ```

2. New language: create `fm1companion/locale/<code>/` (e.g. `fr`) and copy the structure of
   `fm1companion/locale/de/` – the same file names. In each file set the header (`Language: fr`,
   `Plural-Forms: nplurals=2; plural=(n > 1);` for French) and translate every `msgstr`. The msgids stay
   English. Add the language name to `LANGUAGE_NAMES` in `fm1companion/i18n.py` (in its own language,
   e.g. `"fr": "Français"`).

   Any gettext editor works (Poedit, Lokalize, GNOME Translation Editor): open the `.po` file, use
   `messages.pot` to find new strings.

3. Entries marked `#, fuzzy` or with an empty `msgstr` are not used; the app shows the English text.

4. Check the result:

   ```
   python3 tools/i18n_check.py            # placeholders, conflicts, untranslated/missing/obsolete
   python3 tools/i18n_check.py --list     # list the msgids that still need work
   FM1C_LANG=fr fm1-companion --demo      # look at it
   ```

5. Help pages: copy `fm1companion/data/help/de/*.md` to `fm1companion/data/help/<code>/` and translate
   them. Keep the file names (they are the links between pages); missing pages fall back to German.

## Tools

* `tools/i18n_extract.py` – reads the syntax tree of `fm1companion/**/*.py` (without `vendor/` and
  `sims/`) and writes `fm1companion/locale/messages.pot` with source references. `--check` fails if the
  template is out of date.
* `tools/i18n_check.py` – exit code 1 on errors (unparseable files, placeholder mismatches, conflicting
  duplicates). Also prints, per language, how many messages are translated, and the **German-left**
  count: string literals in the code that still look German and are not wrapped in `_()`.
  `--german-left` lists the count per file (`--show` prints each string) – the progress meter while the
  code is being converted.
* `tests/test_i18n.py` – tests for the parser, fallback, plurals, placeholders and language choice.

The test suite runs with the German UI (`tests/conftest.py` and the `tests/ui_*.py` scripts set
`FM1C_LANG=de`), so existing German assertions keep working.
